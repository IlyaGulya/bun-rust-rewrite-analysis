# Crashes, memory retention and npm-normalized report growth

All values use the saved issue snapshot and published npm daily observations through **2026-10-28**. We compare complete calendar days: **2025-11-14–2026-05-13** (181 days) versus **2026-05-15–2026-10-28** (167 days). The merge day, partial report-window endpoints and unpublished downloads are excluded from pooled comparisons. Denominators: **23,077,916** and **70,541,010** npm requests.

| Primary title signal | Before: reports | Before: per million requests | After: reports | After: per million requests | Rate change |
| --- | ---: | ---: | ---: | ---: | ---: |
| Crash / fatal signal | 404 | 17.506 | 190 | 2.693 | −84.6% |
| Explicit memory leak / retained allocations | 15 | 0.650 | 13 | 0.184 | −71.6% |
| Broad memory / OOM / corruption (separate check) | 27 | 1.170 | 25 | 0.354 | −69.7% |

These **report-per-npm-request indicators improved**. This does not establish that Rust reduced confirmed defects or failures per user. The memory-leak numerator is small and barely changes (15 → 13); most of its normalized decline comes from growth in the download denominator. Reports can describe the same underlying defect, old Zig builds, embedded Bun users or JSC behaviour. They are not independently validated incidents attributable to the language change.

The primary leak rule requires explicit memory/allocation-retention evidence in the title. It includes GC roots, retained native memory and memory leaks detected at shutdown, while excluding generic OOM/high memory usage, disk/temp-file growth, file-descriptor leaks and a test-cap flake. The broad memory category is retained separately. The existing crash-title classifier is reused, including its known risk of context-only matches such as crash-report metadata. [Per-issue evidence](data/safety-audit.jsonl) records flags and titles, and the HTML links the 28 primary leak-signal reports in the matched comparison.

Baseline observations are from August and post-merge observations from October. Neither method establishes root causes, severity or unique defects.

## Separate report-growth / audience-proxy chart

For a trailing window W, the new graph plots:

`Q(W) = (reports(W) / downloads(W)) / (pre-period reports / pre-period downloads)`

Equivalently this is `(report daily-mean index) / (download daily-mean index)`, with each index based on its own pre-merge mean. **1** is the fixed pre-period report/download reference; below 1 means fewer reports per npm request than that reference. A rising Q means reports are outpacing npm requests over that interval even if Q remains below 1. This is not a quotient of potentially zero or negative percentage-growth numbers.

The all-report pooled post/pre comparison is **0.435×** (−56.5%). The chart provides all reports, crash reports, explicit leaks and broad memory signals, primary-title/body sensitivity, and 1/7/28-day windows. Rolling rates use ratios of sums; missing/zero download denominators, incomplete report days and nonexistent baselines are gaps. Windows crossing the merge include both periods; summary statistics use separate periods. Pooling the entire post period is not the same as averaging the rolling curve.

“Audience” is proxied by npm requests for package `bun`, across versions. Downloads include CI/repeats, exclude other channels, and do not count unique or active users. Numerator and denominator cover different populations, so Q is not a per-user defect risk. See [download-source limitations](POPULARITY-SOURCES.md).

## Reproduction

`python3 part3/build.py` regenerates the safety export and both plots. `pnpm run verify` independently checks matched-day denominators, category counts, rate changes, memory-leak edge cases and the identity between growth-index ratios and normalized-rate ratios. [safety.py](safety.py) defines the explicit leak/retention rule; [data/safety.json](data/safety.json) stores daily counts and summary values.
