How to read the combined chart

Counts: type stacks use the left report axis, npm downloads the right axis. Growth index: both use the same left scale, with their own pre-rewrite daily mean set to 100. A taller stack than the download line means higher relative growth at that date, not a higher failure probability. Per-million mode divides the report count by npm requests over the same complete dates; a rising stack means that proxy is rising. The download line remains on the labelled right axis in that mode.

With 7-day smoothing, each daily point uses the trailing 7 calendar days. Per-million values divide the sum of reports by the sum of downloads, rather than averaging daily ratios. Missing/unpublished downloads and incomplete report days are gaps in indices and ratios. Daily raw counts can include October 30, which is partial. The pre/post summary uses all complete matched calendar days, excludes the merge day, and does not follow the zoom or legend toggles.

npm supplies a total across Bun versions and one installation channel. It includes CI and repeat requests; it is not an installation count or active-user count. A version filter narrows reports only: there is no historical per-version download denominator here. Never interpret the filtered ratio as that version's defect rate. Report and download populations differ even with all versions selected.

Types remain provisional title signals. One matching type keeps its name; several become “Multiple type signals”; none become “No title signal”. Version extraction checks the Bun field or explicit Bun version against saved official release bases. Unknown and multiple-version reports stay selectable. Canary/debug suffixes are retained; build hashes are grouped. A bare 1.4.0 does not establish stable versus canary.

Definitions, sensitivity and the memory-leak evidence

Matched comparison: 181 pre-merge full days (November 14–May 13), 167 post-merge full days (May 15–October 28). Denominators are 23,077,916 and 70,541,010 npm requests. The first/last partial issue days and merge day are excluded from the table. Dates with unpublished downloads are excluded rather than treated as zero. A report can match both crash and leak; each row counts its reports once and rows must not be added together.

Primary evidence is the title. The sensitivity variant adds at most 2,500 body characters on both sides, removing fenced code, and can pick up incidental mentions. The older plain-text and newer Markdown body snapshots differ in formatting, so this is not an accuracy check. Generic OOM, high RSS and memory corruption remain a separate broad-memory class. Explicit retained allocations and leaks detected at process shutdown are included; disk files, file descriptors and a test's memory-cap flake are excluded from the narrow leak signal.

There are few leak reports, some reports concern the same underlying defect, and titles differ in specificity across periods. The legacy crash classifier also has known contextual false positives (for example, “crash report” metadata). Baseline text/labels were observed in August; post-merge text/labels in October. Arrival dates do not establish Zig/Rust causation, and post-merge reports can concern old Zig builds. npm traffic includes CI and repeats, omits other channels, and does not measure active users. Lower report rates do not establish lower per-user defect risk or prove a Rust effect.

Inspect the classification and its limits

Titles are the primary evidence because old bodies were truncated and triage-label coverage changed. A secondary pass uses the first 2,500 body characters on both sides, removing fenced code and template prompts; it is a sensitivity check, not a validated classifier. Body text still contains incidental mentions. Categories overlap. Manual review of 36 sampled reports found false positives and omissions; these are exploratory counts, not accuracy estimates. Sparse crash titles are more frequent in the baseline, which limits component comparisons.
