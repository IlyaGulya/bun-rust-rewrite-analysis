## Word matches and labels

After-stable issues mention crash **133** times, hang/freeze/deadlock **129**, panic **76**, segfault/access violation **48**, and memory words **127**. The crash-or-hang total is **252 distinct issues (16.9%)**, not 262, because ten issues match both. These are word matches. A panic can be safe error handling. A memory-safety defect requires evidence of its cause. [Saved flags](data/issues.jsonl).

Issues without labels make up **57.1% in August**, **15.5% in September**, and **48.4% in October so far**. The older trend does not continue without interruption. Current labels can also differ from the labels at report time. The [1.4.4 notes](https://bun.com/blog/bun-v1.4.4) describe bulk package-installation and SQL issue closures. Those claims provide context; they do not independently verify our totals.

## What the comparison can show

The release gap ended. The three 30-day closure shares are **26.5% before merge**, **29.6% in the canary period**, and **24.1% after Rust stable**. These are report-date groups across all builds. Stable stayed on Zig during the canary period. The values describe report handling, not a causal language effect.

After 20 August, plain `1.4.x` text cannot identify canary. A version mention can also refer to a dependency or comparison build. All table rows include every build in their date range.

Report counts depend on use, defects, and how often users report problems. We do not measure all these factors. Report growth cannot estimate defect growth or set an upper bound on it. Closure shares also depend on report type and time available for follow-up. Before-merge states remain fixed at the August observation; after-merge states were collected in October. Equal 30-day limits reduce unequal follow-up but do not remove every source of bias.

The estimated open count covers only issues created after the exact merge time. It excludes older repository issues. Earlier reopen and reclose events are unavailable. October and the final day are partial. The collection used several API requests, so records were not all observed at one instant.

## Collection and build

Six monthly search ranges returned **2,578 unique records**. Every response had `incomplete_results=false`. Page counts matched each range total. Ten issues on 14 May preceded the exact merge time, **08:09:34 UTC**, and were excluded. This left **2,568 issues**. [Collection details](data/snapshot.json) record the ranges and time. Releases were collected through the connected GitHub tool. [Source checks](SOURCES-2026-10-30.md) record the event dates.

Run `pnpm install --frozen-lockfile`, `pnpm run rebuild`, and `python3 part2/verify.py`. The offline build uses committed records if the ignored full-body cache is absent. With that cache, it also applies body rules again. `pnpm run refresh` collects new data. Results can change when issues are opened, relabelled, closed, or reopened. The original scripts and 31 checks apply only to the original report.
